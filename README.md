# Listing Automation — Personal AI Seller Hub\n\nPrivate AI-powered seller operations platform for Amazon + Flipkart, built around a reusable Product Brain, marketplace-aware listing knowledge, AI autofill, human clarification, and a safety-gated browser execution layer.\n\nThe repository contains the SellerHub frontend and FastAPI backend. The Listing Automation flow is implemented through six dedicated phases, from marketplace form knowledge to hardened browser execution.\n\n## What the system does\n\n1. Keeps product facts in a reusable Product Brain.\n2. Learns marketplace-specific form structure once.\n3. Creates reusable Master Listing templates for seller + marketplace + category.\n4. Maps marketplace fields to canonical product facts.\n5. Autofills only when confidence and verification rules allow it.\n6. Asks the seller for clarification when information is missing, ambiguous, or unsafe to infer.\n7. Converts approved fill actions into deterministic browser commands.\n8. Validates that the live marketplace page is the correct marketplace and has not changed.\n9. Executes only approved field fills through the browser bridge.\n10. Records step-level results and supports safe recovery of failed executions.\n\n### Safety boundary\n\nThe listing automation layer intentionally does not perform:\n\n- Publish\n- Submit\n- Delete\n- Price changes\n- Inventory changes\n- Arbitrary JavaScript execution\n- Arbitrary navigation or button clicks\n\nThe server remains authoritative for ownership, clarification state, approved actions, execution state, and audit records.\n\n## Architecture\n\n    Product Brain\n         ↓\n    Marketplace Knowledge\n         ↓\n    Master Listing\n         ↓\n    AI Autofill\n         ↓\n    Human Clarification / HITL\n         ↓\n    Browser Execution Plan\n         ↓\n    Marketplace Page Validation\n         ↓\n    Armed Browser Bridge\n         ↓\n    Field-by-field Fill\n         ↓\n    Audit / Results\n         ↓\n    Resume / Recovery\n\n### Six listing automation phases\n\n    Phase 1  Marketplace Form Knowledge\n        ↓\n    Phase 2  Teach AI / Master Listing\n        ↓\n    Phase 3  AI Clarification / Human-in-the-Loop\n        ↓\n    Phase 4  Browser Form Execution\n        ↓\n    Phase 5  Marketplace Browser Bridge\n        ↓\n    Phase 6  Production Hardening & E2E Safety\n\n## Phase 1 — Multi-Platform Marketplace Knowledge\n\nStores marketplace form knowledge per seller account, marketplace, and category.\n\nBackend:\n- MarketplaceFormKnowledge model\n- Alembic migration\n- Schema serialization\n- Schema fingerprinting\n- Marketplace knowledge sync/list/get APIs\n\nFrontend:\n- MarketplaceFormKnowledgeCenter.tsx\n\nMarketplace schemas can be reused instead of rediscovered for every listing.\n\n## Phase 2 — Teach AI / Master Listing\n\nAllows the seller to teach a real marketplace form once and reuse the learned mapping.\n\nBackend:\n- MasterListingTemplate\n- ListingTeachSession\n- Teach/start/complete service flow\n- Seller + marketplace + category scoping\n- Versioned learned templates\n- Marketplace knowledge synchronization\n\nFrontend:\n- MasterListingCenter.tsx\n\nA teach session cannot be completed while unresolved mappings remain.\n\n## Phase 3 — AI Clarification / Human-in-the-Loop\n\nAI does not invent missing product facts. The clarification layer creates an explicit question when a field needs seller input.\n\nRules:\n\n    95–100%  → safe to auto-fill\n    70–94%   → suggestion + confirmation\n    50–69%   → clarification required\n    <50%     → do not fill; ask directly\n    Unknown  → do not invent; ask directly\n\nClarification reasons:\n- VALUE_MISSING\n- FIELD_UNCLEAR\n- VALUE_AMBIGUOUS\n- FORMAT_INVALID\n\nBackend:\n- AutofillClarification\n- Question generation\n- Answer validation\n- Normalization\n- Required/optional handling\n- Session pause/resume behavior\n\nFrontend:\n- AutofillClarificationCenter.tsx\n\nA required unanswered question blocks safe execution.\n\n## Phase 4 — Browser Form Execution\n\nConverts approved autofill actions into deterministic browser commands.\n\nBackend:\n- BrowserExecution\n- BrowserExecutionStep\n- Dry-run planning\n- Armed execution\n- Per-step result recording\n- Execution state machine\n- Audit results\n\nFrontend:\n- BrowserExecutionCenter.tsx\n\nExecution lifecycle:\n\n    planned → armed → running → completed\n                       ↓\n                     failed\n                       ↓\n                     resume\n                       ↓\n                     armed\n\nPending clarification pauses execution planning.\n\n## Phase 5 — Marketplace Browser Bridge\n\nAdds the browser-side contract for Amazon and Flipkart.\n\nSupported hosts:\n- Amazon: sellercentral.amazon.in, sellercentral.amazon.com\n- Flipkart: seller.flipkart.com\n\nThe bridge validates the current marketplace page, verifies the page fingerprint, accepts only safe selectors, fills input/textarea/select fields, dispatches normal input/change events, and reports every step to the backend.\n\nIt does not click submit/publish buttons, navigate arbitrary pages, change price, change inventory, execute arbitrary JavaScript, or accept arbitrary selectors.\n\nSource:\n- frontend/src/browser/marketplaceBrowserBridge.ts\n\nThe bridge is designed to be consumed by a browser extension/content script or future Playwright/browser worker. The repository currently contains the bridge contract and safety layer; it is not itself a packaged browser extension.\n\n## Phase 6 — Production Hardening & E2E Safety\n\nProtections include:\n- Results accepted only for explicitly armed executions.\n- Duplicate identical results are idempotent.\n- Conflicting duplicate results are rejected.\n- Failed executions can be resumed.\n- Successful/skipped steps remain recorded during recovery.\n- Page validation is bound to the session marketplace.\n- Amazon executions cannot validate against Flipkart.\n- Flipkart executions cannot validate against Amazon.\n- Browser and backend use the same normalized SHA-256 page fingerprint.\n- Stale page fingerprints require a fresh plan.\n\nFinal safety model:\n\n    No Publish\n    No Submit\n    No Delete\n    No Price Change\n    No Inventory Change\n    No Arbitrary JS\n\nDetailed documentation:\n- docs/PHASE_14_AUTOFILL.md\n- docs/PHASE_5_MARKETPLACE_BROWSER_BRIDGE.md\n- docs/PHASE_6_PRODUCTION_HARDENING.md\n\n## Frontend\n\nThe frontend is a Vite + React + TypeScript SellerHub application using Tailwind CSS and lucide-react.\n\nMain workspaces include:\n- Dashboard\n- Orders\n- Products\n- Listings\n- Inventory\n- Returns\n- Pricing\n- Advertising\n- Analytics\n- Finance\n- Automations\n- AI Listing Studio\n- AI Seller Copilot\n- Marketplaces\n- Notifications\n- Control Center\n- Diagnostics\n- Reports\n- Settings\n- AI Seller OS\n\nThe Listings workspace is connected to backend listing APIs and includes filtering, marketplace selection, listing actions, export, pagination, and listing details.\n\n### Listing automation UI\n\nWhen the Listings workspace is open, the automation surfaces are available below the main listing table:\n- Master Listing / Teach AI\n- Browser Execution\n- AI Clarification / Human-in-the-Loop\n\nShared module styling is maintained in frontend/src/index.css so the automation modules remain visually consistent with the existing SellerHub dashboard.\n\n## Backend\n\nThe backend uses Python 3.12+, FastAPI, SQLAlchemy, Alembic, PostgreSQL, and Redis-compatible job infrastructure.\n\nCore areas include authentication and seller ownership, Products/Product Brain, Listings, marketplace adapters, marketplace form knowledge, AI autofill, clarification/HITL, browser execution, Orders, Inventory, Returns, Finance, Advertising, automation/jobs, and diagnostics/health checks.\n\n## AI Autofill\n\nSupported modes:\n- draft\n- review\n- auto\n- strict\n\nHigh-risk actions blocked by the autofill safety layer:\n- publish\n- submit\n- delete\n- change_price\n- change_inventory\n\nSemantic form discovery considers name, id, label, placeholder, ARIA label, autocomplete, type, required state, and options.\n\nCanonical Product Brain fields can include TITLE, BRAND, CATEGORY, SKU, HSN, GST_RATE, COLOR, MATERIAL, SIZE, PATTERN, and WEIGHT.\n\nUnknown marketplace fields remain unmapped instead of being guessed.\n\n## Marketplace adapters\n\nThe architecture keeps marketplace-specific details behind adapters.\n\nCurrent listing automation scope:\n- Amazon\n- Flipkart\n\nAdapters provide marketplace-specific schemas, capabilities, field names, validation, and category structure while the Product Brain remains marketplace-neutral.\n\n## Important API endpoints\n\nMarketplace Form Deterministic automation decisions\n- Explicit human clarification\n- High-risk action blocking\n- Marketplace domain allowlisting\n- Page fingerprint validation\n- Step-level execution records\n- Idempotent result handling\n- Recovery without losing successful steps\n- No arbitrary browser JavaScript\n- No hidden marketplace publishing\n\nThe browser layer is deliberately narrower than a general-purpose automation agent.\n\n## Repository structure\n\n    backend/\n      app/\n        api/\n        models/\n        services/\n        marketplaces/\n      migrations/\n      tests/\n\n Do not invent product facts.\n2. Keep marketplace knowledge reusable.\n3. Ask the seller when evidence is insufficient.\n4. Keep deterministic safety rules outside the LLM.\n5. Never bypass high-risk action gates.\n6. Validate the actual browser page before filling.\n7. Audit every execution step.\n8. Recover safely without replaying completed steps.\n9. Keep marketplace-specific details behind adapters.\n10. Prefer explainable automation over opaque automation.\n\n## Roadmap after the six listing-automation phases\n\n1.
